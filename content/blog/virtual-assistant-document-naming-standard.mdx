# Virtual Assistant Document Naming Standards

A document naming standard is a small information-architecture decision. It should help a person retrieve the right file, help a system sort related files, and leave policy decisions to the places that actually govern them.

## Virtual Assistant Document Naming Standards begin with retrieval questions

Start by asking how someone will look for a document later. They may remember a client, a project, an event date, an owner, or a status. The filename should contain the few stable elements that answer the most common searches. When a file also needs substantive review, the [document review process](/blog/virtual-assistant-document-review-process) should identify that work separately from the naming decision.

A useful grammar might be:

`client-project_subject_YYYY-MM-DD_status_vNN_owner.ext`

Treat this as a grammar, not a decorative pattern. Each field has a job. `client-project` groups related work. `subject` names the record in words a person will recognize. The date supports chronology. Status describes the current state. The version distinguishes revisions. The owner points toward the person responsible for the record, not necessarily the person who created the file.

## Choose stable elements first

Use a client or project code only when the code is documented and unlikely to change. Pair it with a readable name when a short code would be meaningless to a new reader. Use a subject that describes the document rather than the action taken to save it.

Dates need a defined meaning. A meeting summary may use the meeting date. A draft policy may use its effective date or review date, depending on the convention. If the file date and the event date both matter, keep one in the filename and the other in metadata or the document body. Do not change a historical date simply to make a folder look tidy.

Status words should come from a small agreed vocabulary. `draft`, `review`, `approved`, and `archived` are easier to search than a collection of personal phrases. Avoid `final-final`, `latest`, or `new version`; those labels record someone’s feeling at one moment and become misleading after the next edit.

## Make the name readable and sortable

Use a date format with year first, followed by month and day: `2026-08-13`. The fixed order lets ordinary filename sorting follow the calendar. Use one separator consistently. Underscores often keep fields visually distinct, while hyphens work well inside a multiword subject. Decide whether spaces are allowed and write that choice down.

Avoid slashes, colons, question marks, quotation marks, and other characters rejected by the storage system. Leave out trailing periods and names that differ only by capitalization. Keep abbreviations documented. A short filename that nobody understands is harder to retrieve than a longer plain-language name.

Compare these examples:

Good: `ACME-ONB_customer-intake_2026-08-13_review_v02_JLee.pdf`

Bad: `final-final customer thing.pdf`

The first name exposes context, subject, date, status, version, and owner. The second forces a reader to open the file and still does not identify the client, the date, or the meaning of “final.”

## Treat versions and collisions as normal

Choose whether version numbers apply to meaningful revisions or every saved copy. Either can work if the rule is consistent. A new version should not erase the previous version when the earlier record may be needed to understand an approval or correction.

Two files can still collide when they share every visible field. Add a narrowly defined discriminator, such as a meeting time or an internal sequence, rather than inventing a vague suffix. `2026-08-13-1430` tells a reader more than `copy2`. If the same document moves through statuses, decide whether the status changes in place or whether each state receives a separate file. That decision belongs to the record owner.

## Migrate a legacy folder in stages

Imagine a folder containing names such as `notes.docx`, `Client meeting new.docx`, `proposal latest.pdf`, and `ACME onboarding 8-1 final.pdf`. Do not rename everything in one blind pass.

First, inventory the files and identify the record owner. Second, map each legacy name to the fields the new grammar requires. Third, flag missing dates, uncertain versions, and possible duplicates. Fourth, rename files whose meaning is clear. Put unresolved items in a review list with links to the originals.

For example, `ACME onboarding 8-1 final.pdf` might become `ACME-ONB_customer-onboarding_2026-08-01_approved_v01_owner-review.pdf` only after someone confirms what “8-1” means, whether the file was approved, and who owns it. If those facts cannot be confirmed, use a temporary review status rather than manufacturing certainty.

Keep a migration log with the old name, new name, date of change, and person who confirmed the mapping. The log helps people find a file when they remember its former name and gives the owner a way to reverse a mistaken mapping.

## Filename, permission, and retention are different

A readable name does not grant access. Permissions belong to the storage system and should follow the organization’s access rules. A filename also does not decide how long a record must be kept. Retention instructions belong in the applicable policy or record-management system.

The [Library of Congress digital formats guidance](https://www.loc.gov/preservation/digital/formats/fdd/fdd000495.shtml) is a useful reminder that identifying a file and preserving it are related tasks, not the same task. A virtual assistant can apply an approved naming convention and flag uncertainty. The authorized owner decides permission, retention, and disputed identity.

## Publish the rule with examples

Put the grammar, field definitions, allowed statuses, forbidden characters, collision rule, and migration procedure in one short reference. Show both good and bad names. Test it against a folder containing old files, duplicate subjects, multiple owners, and a document that changes status.

Review the convention when retrieval repeatedly fails. A standard should serve real searching habits. If a field is never used, remove it. If people always need a missing field, add it deliberately and explain its meaning.

For documents that change over time, pair this naming rule with a written [document version control](/blog/virtual-assistant-document-version-control) practice. The filename can identify a version, but it cannot explain every approval or amendment. Store that history where the responsible reader can find it.

The best test is an ordinary handoff. Give a colleague a folder and ask them to locate a requested record using only the names and the reference page. Watch where they hesitate. Those pauses reveal whether a field is unclear, missing, or doing too much work.
