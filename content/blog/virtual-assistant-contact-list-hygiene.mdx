# Virtual Assistant Contact List Hygiene

Contact-list hygiene is data stewardship: improving consistency while retaining the trail that explains every meaningful change. The goal is not a prettier spreadsheet or a larger audience. It is a dependable record in which a colleague can distinguish an original value, a normalized value, a reviewed correction, and a deliberate suppression. That distinction matters whenever a list is shared between a customer system, an email tool, a shared inbox, and a human team.

## Virtual Assistant Contact List Hygiene: before the cleanup

Start with an inventory of sources and their authority. A CRM may own the account name and relationship status, an order system may own the last transaction date, and an email service may own delivery events. A worksheet can be useful for review, but it should not quietly become authoritative merely because it is easy to edit.

For each field, write down its source, last refresh, transformation, and review status. Preserve the raw value where a change could affect identification or preference. “Acme, Inc.” becoming “Acme Inc” is a display normalization; changing a contact’s organization because a web search found a similar name is a factual edit that needs evidence.

Use a small field-mapping table before the cleanup begins:

| Working field | Authority | Safe transformation | Review trigger |
| --- | --- | --- | --- |
| Full name | Client-approved contact system | Trim spaces; preserve original | Conflicting person identity |
| Organization | Account record | Standardize punctuation | Possible rebrand or merger |
| Email | Contact system plus delivery log | Lowercase for comparison | Shared, bounced, or changed address |
| Preference status | Preference record | Map to controlled labels | Missing date, source, or scope |

This map prevents a reviewer from treating every column as equally trustworthy. It also makes a later rollback intelligible.

## Before: normalize without erasing provenance

Create comparison values separately from source values. Trim accidental spaces, standardize obvious casing, and use one agreed phone-number representation for matching. Keep a column such as `original_email` or an immutable source snapshot instead of overwriting the only copy. Record the rule and its version in the change log.

Normalization must be conservative. A nickname is not automatically a different legal name, and a missing apartment number is not permission to invent one. Country-specific address formats deserve review rather than a universal rewrite. When a value cannot be safely interpreted, leave it unchanged and mark it for a person who knows the record.

## Before: separate deterministic matches from reviewed matches

Deterministic deduplication uses a strong, explicit key, such as the same normalized email from the same authoritative source. Even then, inspect exceptions. A role inbox can be intentionally shared by several people, and an address such as support@example.com may represent a function rather than an individual.

Reviewed deduplication is different. Similar names, matching domains, and nearby phone numbers are clues, not proof. Put candidate clusters into a review queue with the evidence side by side. A reviewer should choose merge, keep separate, or insufficient evidence. Never make a fuzzy match disappear simply because the list needs a lower count.

## Before: treat inboxes, bounces, and preferences as distinct

A shared inbox needs an owner and a purpose label. Do not attach every message sent to a role address to the last person who answered it. Bounced addresses also need classification: a temporary delivery failure, a permanent rejection, and an address that has been replaced are different states.

Consent and communication preferences require their own provenance. Keep the source, date, scope, and current status where the client’s system provides them. A suppression should remain visible as a suppression; deleting the row can make a later import look like permission to contact the person again. If the status is ambiguous, pause the change and ask the responsible owner rather than guessing.

## The worked duplicate-cluster example

Imagine three records arrive in a review queue:

- Record A: “Mira Patel,” `Mira.Patel@Northstar.example`, source CRM, last reviewed in April.
- Record B: “Mira P.”, `mira.patel@northstar.example`, source event sheet, no preference date.
- Record C: “Northstar Support,” `support@northstar.example`, source shared inbox, owner listed as Customer Care.

A and B share a comparison email, but B’s source is weaker and its preference history is incomplete. The reviewer can merge B into A while retaining B’s source reference and noting that A remains the surviving record. C must stay separate because its address represents a function, not a confirmed person. If the team later proves that A owns that inbox, that is a new reviewed fact, not an automatic consequence of the matching domain.

The resulting log might say: “Candidate B merged into A after exact normalized-email match; original B identifier retained in merge history; preference metadata not promoted because its source date was absent. C retained as shared inbox; no person assignment made.” That sentence explains both the action and the restraint.

## After: record the transformation and the rollback

Take a dated snapshot before applying changes. Give every merge a stable operation ID and capture the surviving identifier, retired identifier, fields selected, reviewer, reason, and timestamp. For a field-level correction, record old value, new value, source authority, and evidence. Keep suppression changes in the same audit trail, but do not expose private contact details in a broad report.

A rollback should be practical, not theoretical. Store the snapshot where the client’s access rules permit it, test restoring a small sample, and document how an operator would reverse a merge without reactivating a suppressed address. Compare counts by meaningful status, not only total rows. A lower total might reflect intentional consolidation, while a lower suppressed count could signal a dangerous mistake.

## After: perform a human review pass

Review every uncertain cluster and a sample of deterministic changes. Look specifically for shared inboxes, bounced addresses, international formatting, household records, and contacts whose preferences are scoped to a particular channel. Ask whether the cleaned record still lets someone answer four questions: where did this value come from, what changed, who approved it, and how would we undo it?

Contact-list hygiene is complete when the list is easier to use and its history is still legible. A clean record does not claim certainty where the evidence is thin. It makes uncertainty visible, protects suppression choices, and leaves the next steward enough context to continue carefully.
