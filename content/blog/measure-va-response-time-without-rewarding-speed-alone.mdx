# Measure VA response time without rewarding speed alone

## How to approach: Measure VA response time without rewarding speed alone

A response-time measure is useful only when it is paired with a quality measure. If the team is rewarded for speed alone, it will send faster and less complete replies. Start with the question the measure should answer, such as whether clients receive a useful first response within the promised window. Test the rule on one real task before applying it to the queue.

Define the start and stop events before collecting data. The start might be the moment a request arrives in the shared queue, not the moment someone opens it. The stop might be the first substantive reply, not an automated acknowledgment. Ambiguous events produce a number that cannot be defended.

## Separate acknowledgment from resolution

A fast acknowledgment is not the same as a fast resolution. Measure them separately so the team can see whether the first reply actually helps. A reply that says we are looking into it may meet an acknowledgment target while leaving the client without information. Test the rule on one real task before applying it to the queue.

Set a quality condition for the first reply. It should name the next step and the expected date, or ask a specific question. A reply that only acknowledges the message should not count as a complete first response. Review the first few notes together before the process expands.

## Use a window that fits the work

A single target for every request will punish complex work and reward trivial work. Group requests by type and set a window for each group. A calendar change and a contract review do not need the same response time. If the source is unclear, route the question instead of guessing.

Review the windows with the team before publishing them. A target that the team believes is impossible will be gamed. A target that is too loose will not improve the client experience. Keep the original note beside the corrected version.

## Check accuracy on a sample

Pull a sample of fast responses and check whether they were accurate and complete. A fast response that creates a follow-up question is not a good outcome. Record the error rate beside the response time so the two are read together. Ask whether a new reviewer could act on the record without a conversation.

If speed improves while accuracy falls, the measure is doing harm. Change the target or the review step before celebrating the faster number. Separate what was observed from what was assumed. Write the deadline as a date and a local time.

## Watch for queue gaming

Look for requests that are closed quickly without a real answer. Look for replies that move the work to another queue and count as resolved. Look for cases where the clock starts late because someone delayed opening the request. Keep the boundary visible in the place where the work is assigned.

A measure that can be improved by moving work rather than doing it will be gamed. Add a check for reopened requests and for replies that only ask the client to wait. Ask whether a new reviewer could act on the record without a conversation. Keep the original note beside the corrected version.

## Report the measure with its limits

Report the response time with the sample size, the request mix, and the accuracy rate. A single average hides the slow tail where the client experience is worst. Show the share of requests that met the window and the share that were reopened. Keep the original note beside the corrected version.

Review the measure quarterly and change it when the work changes. The goal is a useful first response, not a faster clock. Separate what was observed from what was assumed. Update the template when the same question appears twice.
