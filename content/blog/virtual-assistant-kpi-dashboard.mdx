# Virtual Assistant KPI Dashboard Preparation

A useful KPI dashboard is a collection of small measurement contracts. Each contract tells a reader what a number means, where it came from, when it was refreshed, and what question it can answer. A virtual assistant maintaining the dashboard can protect that clarity without pretending to explain the business result. The job is to preserve evidence and make uncertainty easy to see.

## Virtual Assistant KPI Dashboard Preparation: Start with the decision

Before adding a card, write the decision it is meant to support. A service team may need to decide whether to add coverage to a queue. A manager may need to decide whether a request is waiting on an internal review. A marketing lead may want to inspect movement between stages. These are different questions, even if each is described as performance.

If a measure has no reader or decision, place it in a source worksheet rather than the headline view. This simple test keeps the dashboard from becoming a museum of every available field. It also gives the assistant a safe boundary: organize the evidence for a decision, but do not manufacture a conclusion when the evidence is incomplete.

## Build a measurement contract for every card

Give each metric a short contract stored beside the dashboard or in its documentation. Record the metric owner, numerator, denominator, source, refresh cadence, cut-off time, expected lag, target provenance, exception note, and revision history.

The owner is accountable for meaning, not necessarily the person who updates the file. The numerator and denominator describe the exact population. The source identifies the system or report that can be checked. Refresh cadence says how often the value should be revisited, while cut-off time prevents a late record from quietly moving an earlier period. Expected lag tells a reader when a value is provisional.

Target provenance matters because a target can come from a plan, a signed service standard, a leadership decision, or a temporary working assumption. Labeling that origin prevents an assistant from presenting an unapproved target as an official commitment. An exception note explains exclusions, missing records, changed definitions, or unusual events. Revision history records who changed the contract, when, and why.

## Resolve the definition before calculating

Suppose one stakeholder asks for response rate. The operations report counts every incoming request, while the customer team counts only requests that reached a staffed queue. Both calculations may be internally correct. They answer different questions.

The assistant should write the dispute in neutral terms: “Operations definition includes all requests received during the window. Customer team definition includes requests assigned to the staffed queue. Owner to confirm which population supports the weekly coverage decision.” Then pause the headline metric or show both labeled versions. Do not select the more favorable result, average the two, or change the label to hide the disagreement.

When the owner chooses a definition, record the decision in the contract and note the effective date. Historical values should not be restated silently. If a restatement is requested, preserve the previous series and identify the revision so readers can distinguish a business change from a data correction.

## Treat time as part of the measurement

A dashboard can look precise while mixing incompatible clocks. State whether the window uses calendar days, business hours, local time, or the source system’s timezone. Define whether the end date is inclusive. Mark the current period as partial when records are still arriving.

Lag deserves its own label. A completed interaction may be available immediately, while a verified outcome may arrive days later. Showing a provisional value with its expected completion date is more honest than filling the gap with an estimate. If a source is unavailable, write “not refreshed” and preserve the last known timestamp. Never convert a stale value into a current one by changing the display date.

## Put exceptions beside the number

An annotation should answer what changed, which periods it affects, and whether comparison remains valid. Examples include a queue migration, a new intake field, a closed office day, or a source export that omitted a segment. Keep the note factual. “The export omitted the regional queue” is useful. “The team performed poorly” is a conclusion that requires a defined analysis and appropriate owner review.

Use a small status vocabulary such as current, provisional, delayed, definition changed, and unavailable. Define those labels in the dashboard guide. Consistent labels help a reader scan the page without treating every warning as the same kind of problem.

## Review the dashboard like a reader

The following review table gives an assistant a practical inspection sequence:

| Review question | Evidence to inspect | Acceptable result |
| --- | --- | --- |
| Can the reader name the decision? | Card title and nearby purpose note | Decision is explicit |
| Can the value be reproduced? | Source, filters, numerator, denominator | Another reviewer can trace it |
| Is the period complete? | Cut-off time and refresh timestamp | Current or clearly provisional |
| Is the target trustworthy? | Target provenance record | Origin and effective date are shown |
| Are exceptions visible? | Annotation and exception note | Missing or changed data is labeled |
| Can history be explained? | Revision log | Definition changes have reasons |

If a card fails a question, fix the documentation or mark the limitation before polishing colors and layout. Visual refinement cannot repair an undefined denominator.

## Keep maintenance separate from interpretation

A virtual assistant can check that a source arrived, apply an approved filter, calculate a documented formula, compare timestamps, and route a discrepancy to the metric owner. The assistant should not infer why a result changed, assign blame, invent a target, or describe a trend as meaningful without the agreed method.

For broader guidance on connecting measures to management use, consult the [U.S. Government Accountability Office performance measurement guide](https://www.gao.gov/products/gao-20-701g). ## End with a traceable handoff

Each update should leave a short maintenance note: refresh completed, source timestamp, exceptions found, questions awaiting an owner, and next review date. That note creates continuity without adding interpretation. Over time, the dashboard becomes more dependable because every number carries its definition, limits, and history with it.
