# Build a handover checklist for a planned VA absence

## How to approach: Build a handover checklist for a planned VA absence

A planned absence is easier than an emergency, but it still fails when the handover is left to memory. Start the checklist at least a week before the absence. The checklist should name the work, the owner, and the date the backup takes over. Name the owner in the same line as the action.

Keep the checklist short enough to finish. A long document that is written the night before is not a control. Use the same template for every absence so the team learns what information is actually needed. Update the template when the same question appears twice.

## List the open work and the next deadlines

Write each open task with its status, next deadline, and source record. Include the tasks that are waiting on someone else, because those are the ones most likely to be forgotten. Mark the tasks that must be completed during the absence. A control that depends on memory is not yet a control.

Separate work that can wait from work that cannot. A backup who tries to do everything will do the important work poorly. The checklist should say what will pause and who knows about the pause. Separate what was observed from what was assumed.

## Confirm access and tools

Check that the backup can log in, open the files, and use the templates needed for the must-do work. Test the access before the absence. Record any approval that is still pending and the person who owns it. Record the observation time so the next reviewer can tell when the evidence was checked.

Keep the access list current. A tool that was added last month may not be in the checklist. Ask the backup to open each tool and confirm the expected screen. A successful login is not the same as the right permission.

## Record contacts and preferences

List the client contacts, the internal approvers, and the escalation path. Include the preferred channel and the times when a response is expected. A name without a role or a channel is not enough. Keep the evidence with the record rather than in a separate log.

Note any customer preference that affects the work, such as a do-not-call instruction or a required subject line. The backup should not have to rediscover a preference that the primary already knows. Keep the original note beside the corrected version. Test the rule on one real task before applying it to the queue.

## Name the decisions that must wait

State what the backup may decide and what must wait for the primary or the manager. A schedule change may be fine, while a refund or a contract change is not. Name the person who can approve an exception during the absence. A short note with four fields is easier to use than a long narrative.

Record the boundary in the handover note and review it with the backup. A boundary that is only in a policy file will be missed when a client asks for something urgent. If the source is unclear, route the question instead of guessing. Update the template when the same question appears twice.

## Close the handover when the primary returns

Review what happened during the absence and update the checklist. Note the questions the backup had to ask and the tasks that were missed. Those are the gaps to fix before the next absence. Separate what was observed from what was assumed.

Thank the backup and share the learning with the team. A handover that is only reviewed when something goes wrong will keep producing the same problems. Review the first few notes together before the process expands. Test the rule on one real task before applying it to the queue.
